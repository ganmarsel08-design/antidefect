# Слепой тест №2 — план заморозки и запуска (ЧЕРНОВИК, без запуска)

Только синтетические данные. Программа к реальным пациентам не допускается.

## Предусловия (все — до получения набора №2)
1. PR №12 и №13 одобрены рецензентом и слиты владельцем в рабочую ветку; решение владельца по CI для неизменённого контроля этапа 7 принято.
2. Программа для теста — **один коммит** рабочей ветки после слияния. Его SHA и SHA-256 файлов `extract.js`, `docx.js`, `case-builder.js`, `rules-engine.js`, `derive.js`, `expert-view.js`, `expert-app.js`, `pilot-rules.json`, `expert-decisions.json` вносятся в манифест оценщика.
3. Оценщик 1.5 (отдельный PR, утверждается рецензентом до получения набора):
   - класс «часть правила не оценивалась» отдельно от «иное» (замечание к отчёту №1);
   - поле `first_abx_dose_administered_at` не считается дозовым (шаблон `*_dose_*` → явный список дозовых полей);
   - валидатор: противоречие ловушки `must_not_value: "any"` действующему факту — ошибка набора;
   - проверка встроенных объектов и концевых сносок в эталоне чтения DOCX;
   - время записи не размечается фактом (единственный вариант): валидатор допускает `time_kind` только `event_time`; ловушка `document_time_as_event` срабатывает, если программа выдала время записи как время события;
   - тесты на каждое изменение; версии 1.4 и результаты №1 не меняются.
4. Задание автору `blind2-author-1.0` (на основе черновика `author-task-delta-draft.md`) утверждено рецензентом.

## Роли
См. раздел 1 черновика задания: разработчик не видит набор и эталон №2 до фиксации SHA программы и первого прогона; исправления после раскрытия → следующий прогон регрессионный.

## Порядок
1. Владелец передаёт задание новому независимому автору.
2. Получение архива → формальная проверка валидатором 1.5 → при ошибках набор возвращается автору (эталон исполнитель не правит).
3. Врачебная проверка правдоподобия 2–3 историй владельцем.
4. Заморозка: SHA-256 архива и каждого файла, манифест 1.5, SHA программы → публикация хэшей рецензенту **до** запуска.
5. Отдельное разрешение владельца → один прогон, одна оценка.
   **Независимость первого прогона (требование рецензента):** разработчик и оценщик — одна модель, поэтому разведение достигается порядком, а не обещанием. (а) До раскрытия набора фиксируются и публикуются неизменяемые SHA: программы, `scorer/` 1.5, манифеста набора (SHA-256 архива и каждого файла) и скрипта запуска. (б) Эталон (`gold`) в репозиторий и в доступ разработчика не передаётся: его хранит владелец; оценщик получает его только на шаге оценки. (в) Первый прогон выполняет автоматический job на этих SHA (CI или единый скрипт `run.js` с проверкой RUN-MANIFEST), без правок кода и без чтения эталона; сырой вывод извлекателя записывается только для чтения и хэшируется до оценки. (г) Оценка — отдельный шаг на уже зафиксированном выводе. (д) Любая правка программы, оценщика или набора после раскрытия — новый пункт «изменение после раскрытия»; последующий прогон регрессионный, не слепой. Если автоматический job по какой-либо причине невозможен, владелец вместо него назначает независимого исполнителя первого прогона.
6. Отчёт: метрики против тех же порогов, кластерный бутстреп, нулевые критерии с k/N, влияние на 30 правил, «не проверено», отклонения. Поправки эталона — отдельным файлом, первичные метрики не переписываются.

## Что считается слепым
Только набор №2, которого исполнитель не видел до заморозки. Набор №1 и любые повторные прогоны на нём — регрессионные, не слепые, и в отчётах так подписываются.
