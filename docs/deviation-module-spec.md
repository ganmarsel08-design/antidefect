# ТЗ: модуль «Отклонение от протокола + обоснование» (Антидефект, версия 0.6)

Статус документа: **базовая версия завершённого этапа 3** (тестовый прототип принят 18.11.2026 после окончательной проверки PR №5). Только синтетические данные. Изменения после этой версии — через новые PR этапа 4 и далее.

Изменения относительно 0.5 (финальная проверка этапа 3):
- подтверждение полноты реестра в браузере — только заявление эксперта (`verification: заявлено_экспертом`) с перечнем проверенных протоколов, версией реестра и основанием; положительный вывод по «не урегулировано» остаётся заблокированным до сверки с официальными источниками (этап 4);
- экспертная оценка применимости исследования привязана к клиническому контексту (назначение, схема, показания) и к источнику; при их изменении нужна повторная оценка, библиографическое подтверждение сохраняется.

Изменения относительно 0.4 (проверка PR №5):
- черновик обоснования строится по результату движка (`clinical.relation`, статус, блокировки), а не по выбору пользователя; при неполной проверке — только осторожные формулировки (`buildJustificationDraft`, раздел 17);
- результат и черновик явно указывают основу: анализируются только вручную введённые сведения, текст истории не разбирается;
- полнота реестра: «заявлена» (выбор пользователя) и «подтверждена» (`attestRegistryCompleteness`, число протоколов должно совпадать); при заявленной, но не подтверждённой полноте положительный вывод заблокирован;
- все подтверждения и решения в браузере помечены как тестовые (`test_only`, `assurance`) до внедрения авторизации и защищённого журнала;
- изменение исходных данных или настроек делает результат устаревшим (`input_fingerprint`, `isStale`); решение эксперта и черновик по устаревшему результату не принимаются; повторная проверка (`reevaluate`) сохраняет историю решений и прежние результаты.

Изменения относительно 0.3:
- пороги сигналов тестовой версии (раздел 7);
- неполный реестр применимых протоколов не позволяет установить «не урегулировано» (3.1, 6);
- неподтверждённая редакция или актуальность применимого протокола блокирует окончательный положительный вывод (5.5);
- библиографическая проверка и экспертная оценка учитываются только с проверяемым происхождением (4, блок 3);
- проверка 12 цифр не считается обезличиванием (раздел 10);
- интерфейс аудита (раздел 16).

Изменения в 0.3 относительно 0.2:

- клиническое соответствие и полнота обязательной документации — две отдельные оценки; положительный клинический статус не скрывает отсутствующие записи (раздел 5.3);
- противоречия в клинических данных выявляются отдельно (`conflict_detected`) и не подменяются статусом «Недостаточно данных» (раздел 5.4);
- сигналы безопасности получили серьёзность, уверенность и подтверждённость; срочность определяется по порогу (раздел 7);
- библиографическая проверка источника (PubMed) отделена от экспертной оценки доказательств (раздел 4, блок 3);
- приняты решения по открытым вопросам версии 0.2 (раздел 13).

## 1. Принцип

Единственный критерий аудита: помощь оказана по действующему протоколу РК. Отклонение от протокола не является дефектом само по себе, но каждое существенное отклонение должно иметь проверяемое обоснование. Отсутствие рекомендации в протоколе не означает запрет назначения. Наличие публикации не означает, что назначение обосновано.

Программа не выносит окончательного решения и не объявляет врача допустившим дефект. Она показывает, чего в обосновании хватает и чего нет. Окончательное решение принимает назначенный врач-эксперт или уполномоченная комиссия медицинской организации.

## 2. Объект проверки

Проверка выполняется отдельно по каждому назначению или решению: препарат, доза, кратность, путь введения, длительность, метод, исследование.

## 3. Два независимых параметра

### 3.1. Отношение к протоколу

| Значение | Условие |
|---|---|
| Соответствует | Протокол регулирует вопрос, назначение в пределах указанного (включая допустимый диапазон) |
| Отличается | Протокол регулирует вопрос, назначение выходит за его пределы |
| Не урегулировано | В проверенном наборе применимых протоколов прямая рекомендация не найдена |
| Невозможно проверить | Нет данных для сравнения, нет ссылки на протокол (номер, раздел, цитата), редакция на дату помощи не подтверждена, либо для «не урегулировано» нет перечня просмотренных протоколов и сведений о полноте реестра, либо в реестре не хватает применимых протоколов |

Формулировка для «не урегулировано» всегда такая: «прямая рекомендация не найдена в проверенном наборе применимых протоколов». Формулировка «в протоколах РК рекомендации нет» запрещена.

### 3.2. Подтверждение показаний

| Значение | Условие |
|---|---|
| Подтверждены | В истории есть данные, соответствующие показанию |
| Не подтверждены | Проверена полная история, подтверждающих данных нет |
| Недостаточно данных | Предоставлен только фрагмент истории или данных мало |

«Не подтверждены» допустимо только при полной истории. Параметры 3.1 и 3.2 независимы.

### 3.3. Допуски по дозам

Универсальный допуск не применяется. Сравниваются конкретные параметры (доза на кг, разовая и суточная доза, интервал и т. п.) с диапазонами, прямо установленными протоколом или инструкцией. Назначение внутри диапазона отклонением не считается. Если диапазоны заданы, результат сравнения имеет приоритет над заявленным отношением.

## 4. Пять блоков проверки

Каждый факт хранится с источником: дата, время, фрагмент истории, раздел документа.

1. **Назначение.** Что назначено; результат поиска по протоколам (раздел 6); значение 3.1; в чём отличие.
2. **Показания.** Факты из истории и значение 3.2. Программа ничего не домысливает.
3. **Научное обоснование.** Две независимые проверки:
   - **Библиографическая (автоматическая):** источник существует; PMID/DOI, название, авторы, год, журнал совпадают с указанными. Инструмент — NCBI E-utilities (PubMed) или ручная проверка. Результат: найден / не найден / метаданные не совпадают. Эта проверка ничего не говорит о качестве и применимости исследования.
   - **Экспертная оценка (только человек):** применимость к ребёнку (совпадает / частично / не совпадает / не определено) и соответствие схемы (да / частично / нет / не определено). Записывается, кто оценил.
   Источники программа не выдумывает.
   **Происхождение.** Обе проверки учитываются, только если созданы функциями модуля `attestBibliographic` / `attestExpertAssessment` с указанием проверяющего, способа и времени. Значения из входного JSON, импорта или вставки подтверждением не считаются: источник получает статус «нужна проверка», а программа выдаёт предупреждение. После сериализации (выгрузки) подтверждения теряют силу. Ограничение тестовой версии: защита от случайного или импортированного «подтверждения», но не от умышленной подделки в браузере; для реальной работы нужна серверная подпись и учётные записи.
4. **Документация.** Запись врача с обоснованием, оценка пользы и рисков, мониторинг, консилиум, согласие. Для каждого: найдено / не найдено в предоставленном фрагменте / не найдено после проверки полной истории.
5. **Вывод.** Клинический статус (раздел 5), состояние документации (5.3), сигналы безопасности (раздел 7), противоречия (5.4).

## 5. Статусы

### 5.1. Приоритет

Программа предлагает один клинический статус. Выбирается первый подходящий.

| № | Статус | Условие |
|---|---|---|
| 1 | Требуется срочная оценка эксперта | Есть сигнал безопасности выше порога срочности (раздел 7) |
| 2 | Требуется оценка эксперта | Обнаружено противоречие (5.4) или есть сигнал безопасности ниже порога срочности |
| 3 | Недостаточно данных | Отношение «невозможно проверить», показания «недостаточно данных», либо при отклонении обязательные записи «не найдены во фрагменте» |
| 4 | Соответствует протоколу | Отношение «соответствует», показания подтверждены |
| 5 | Обоснованное отклонение | Отношение «отличается» или «не урегулировано», выполнены все условия 5.2 |
| 6 | Требуется оценка эксперта | Все условия 5.2 выполнены, кроме экспертной оценки применимости или схемы |
| 7 | Отклонение документировано не полностью | Остальные случаи; перечисляется, чего именно нет |

Статус «Потенциальный дефект» автоматически не ставится. Его может установить только эксперт (5.6).

### 5.2. Условия «обоснованного отклонения»

Все одновременно:
- показания подтверждены;
- хотя бы один источник предъявлен, прошёл библиографическую проверку и оценён экспертом;
- применимость «совпадает» и схема «совпадает», либо хотя бы одно «частично» при наличии записи врача о причине переноса данных;
- запись врача с обоснованием найдена;
- консилиум проведён, если он обязателен (раздел 8).

Статус не означает, что назначение доказанно правильное и что комиссия его примет.

### 5.3. Полнота документации

Оценивается отдельно от клинического статуса по списку обязательных записей:
- обязательные записи из правила реестра (для назначений по протоколу);
- для отклонений — всегда запись врача с обоснованием, плюс консилиум, если он обязателен, плюс записи из настроек.

Состояние: полная / неполная (не найдено в полной истории) / не определена (не найдено во фрагменте) / не требуется.

Итоговая строка заключения всегда показывает оба результата, например: «Соответствует протоколу; документация неполная: запись врача с обоснованием». Положительный клинический статус не скрывает отсутствующих обязательных записей.

### 5.4. Противоречия (`conflict_detected`)

Противоречие — два факта из истории, которые не могут быть верны одновременно (например, разные результаты одного посева). Каждое противоречие хранится парой фактов с источниками. При любом противоречии статус «Требуется оценка эксперта» (приоритет 2), а не «Недостаточно данных».

### 5.5. Блокировка положительного вывода

Статусы «Соответствует протоколу» и «Обоснованное отклонение» окончательными быть не могут, если хотя бы у одного применимого протокола (совпавшего, а для «не урегулировано» — у любого просмотренного) редакция на дату помощи не подтверждена или актуальность в реестре «не проверен». В этом случае предлагается «Требуется оценка эксперта» с отметкой «положительный вывод заблокирован» и перечнем причин. Отрицательные находки (чего не хватает) не блокируются и показываются как есть. Протокол со статусом «заменён», действовавший на дату помощи, блокировки не вызывает.

### 5.6. Ручное изменение

Эксперт может изменить любой статус, включая установку «Потенциальный дефект», с обязательным указанием причины и источника. Исходный результат программы сохраняется; все изменения записываются в журнал.

## 6. Поиск по протоколам

Для каждого назначения сохраняется: перечень просмотренных протоколов (номер, дата утверждения, редакция, статус в реестре, подтверждение редакции на дату помощи), проверенные разделы, критерии применимости, дата поиска, полнота реестра (сколько протоколов, какие применимые не внесены).

Статус протокола в реестре: действует / заменён / не проверен. Если в реестре нет хотя бы одного применимого протокола, «не урегулировано» не устанавливается (отношение «невозможно проверить»). Протоколы, актуальность которых не подтверждена официальным источником, имеют статус «не проверен». Старый год утверждения сам по себе не означает отмену.

Если редакция протокола на дату оказания помощи не подтверждена, отношение к протоколу «невозможно проверить».

## 7. Сигналы безопасности

Сигнал — предупреждение о риске, а не заключение о дефекте. Виды: возможное противопоказание, возможное превышение дозы, возможное несоответствие пути введения, возможное несоответствие интервала.

Каждый сигнал содержит:
- **серьёзность:** низкая / средняя / высокая / критическая;
- **уверенность:** низкая / средняя / высокая;
- **подтверждённость:** подтверждён документально или нет;
- цитату требования, факт из истории и источник.

Пороги тестовой версии (утверждены при проверке PR №4):

| Серьёзность | Уровень |
|---|---|
| Критическая | Срочная экспертная проверка независимо от уверенности (цитата требования, факт и источник обязательны) |
| Высокая | Срочно, если подтверждён или уверенность не ниже средней; иначе обычная экспертная проверка |
| Средняя | Обычная экспертная проверка; срочность повышает эксперт (ручное решение) |
| Низкая | Предупреждение; статус не меняет |

Срочный сигнал — статус 1, обычная проверка — статус 2.

На этапе 2 сигналы поступают на вход модуля. Автоматическое формирование сигналов из инструкций препаратов — этап 4.

## 8. Консилиум

Консилиум не обязателен автоматически при отклонении. Обязателен только при наличии нормативного или локального основания, указанного в настройках (без указания основания настройка не принимается). В остальных случаях программа рекомендует консилиум при высоком риске: применение вне инструкции, высокий риск по отметке врача, любой сигнал безопасности.

## 10. Требования к работе с данными

- До проверки правовых оснований обработки, требований к хранению и информационной безопасности в РК используются только синтетические или обезличенные истории.
- Псевдонимизация не равна полной анонимизации. Отметки согласия в программе недостаточно для работы с реальными данными.
- Модуль и интерфейс отклоняют данные с последовательностью из 12 цифр (возможный ИИН), интерфейс предупреждает о похожих на телефон номерах. Это простые проверки, а не обезличивание: ФИО, даты, редкие диагнозы они не находят. Реальные истории не подключаются.
- Исходная история не изменяется: модуль только читает.
- В PubMed передаются только библиографические данные (PMID, DOI, название), никаких данных пациента.
- ИИ используется только для извлечения фактов. Статус определяется детерминированными правилами разделов 3–8.

## 11. Пример

Назначен лечебный курс противогрибковой терапии ребёнку без порока развития диафрагмы.

В проверенных применимых разделах протоколов №4 (РДС), №185 (сепсис) и №231 (пороки развития диафрагмы) не обнаружена универсальная схема лечебной противогрибковой терапии для данной клинической ситуации. Отношение к протоколу: «не урегулировано».

Назначение требует оценки клинических показаний, микробиологических данных, факторов риска, научного обоснования и документированного решения врача. Само отсутствие прямой рекомендации не является основанием для квалификации назначения как дефекта.

Это пример логики, а не подтверждение правильности конкретного назначения.

## 12. Критерии приёмки

1. Параметры 3.1 и 3.2 независимы; есть тест «отличается» + «показания не подтверждены».
2. «Не урегулировано» не ставится без перечня просмотренных протоколов и полноты реестра.
3. «Недостаточно данных» и «не найдено во фрагменте» не превращаются в «не документировано» или в дефект.
4. «Потенциальный дефект» автоматически не ставится.
5. Срочность сигнала определяется по серьёзности, уверенности и подтверждённости; несрочный сигнал даёт статус 2.
6. Противоречие даёт статус 2, а не «Недостаточно данных».
7. Клиническое соответствие при отсутствии обязательной записи показывает «документация неполная».
8. Библиографическая проверка без экспертной оценки не даёт «Обоснованного отклонения».
9. Назначение внутри диапазона протокола не считается отклонением.
10. Ручное изменение статуса сохраняет исходный результат.
11. Исходные данные не изменяются.
12. Не менее 15 синтетических случаев, не менее 2 на каждый автоматический статус.
13. Неполный реестр применимых протоколов не даёт «не урегулировано».
14. Неподтверждённая редакция или актуальность применимого протокола блокирует положительный вывод; «заменён», но действовавший на дату помощи, — не блокирует.
15. Экспертная оценка и результат PubMed из входных данных без подтверждения не учитываются; после сериализации подтверждения теряют силу.
16. Пороги сигналов по таблице раздела 7.
17. Черновик следует результату движка; при неполной проверке — осторожные формулировки.
18. Заявленная, но не подтверждённая полнота реестра блокирует положительный вывод.
19. Все подтверждения и решения помечены как тестовые.
20. Изменённые данные делают результат устаревшим; решение по устаревшему результату отклоняется; повторная проверка сохраняет историю.
21. Подтверждение полноты реестра в браузере не снимает блокировку положительного вывода; хранит перечень протоколов, версию и основание.
22. Изменение назначения, схемы, показаний или источника после экспертной оценки требует повторной оценки; библиография сохраняется.

## 13. Решения по открытым вопросам

| Вопрос | Решение |
|---|---|
| Статусы для A/B/C | Единый набор статусов; отношение к протоколу и показания — отдельные параметры |
| Несущественные отклонения | Без универсального допуска; внутри диапазона — не отклонение |
| Консилиум | Обязателен только при нормативном или локальном основании; иначе рекомендация по риску |
| Актуальность 29 протоколов | Пока «не проверен». Каждый сверяется по официальным источникам с фиксацией редакций и дат. Реестр не заполняется предположениями |
| Кто подтверждает «проверено» | Назначенный врач-эксперт или уполномоченная комиссия |
| PubMed | Автоматическая библиографическая проверка (NCBI E-utilities); применимость и достаточность — экспертная оценка |
| Инструкции к препаратам | Приоритет — официальные государственные реестры РК (НЦЭЛС и МИ), с версионированием; международные источники — дополнительные, с явной маркировкой |

## 15. Этапы разработки

1. Модель данных и независимые проверки — `engine/deviation-engine.js` (готово).
2. Детерминированный механизм статусов с тестами — `engine/test/` (готово).
3. Простой интерфейс аудита и формирования обоснования — `engine/audit.html` (готово, тестовая версия).
4. Подключение и верификация реестра клинических протоколов РК (отдельный этап, `docs/stage4-registry-plan.md`); инструкции к препаратам; формирование сигналов.
5. Синтетические клинические тесты и независимая проверка.

Реальные персональные данные не используются. `neo-pro` и `main` не изменяются. Изменения — через PR, без автоматического слияния.

## 16. Интерфейс аудита (этап 3)

Одна страница `engine/audit.html`, без сервера и без сети.

1. Предупреждение и отметка: текст синтетический или обезличен пользователем. Без отметки проверка не запускается.
2. Эксперт (ФИО или псевдоним, роль) — обязателен для подтверждений и решений. Пациент — псевдоним.
3. Текст истории: вставка или файл .txt; выбор «полная история / фрагмент».
4. Назначения: карточка на каждое. В карточке — статус, итоговая строка, список конкретных проблем. Вкладки:
   - «Данные» — вопросы простым языком; противоречия, сигналы, «вне инструкции» — в свёрнутом блоке;
   - «Обоснование» — пять блоков и черновик обоснования для комиссии (только из введённых данных, пропуски в [скобках]);
   - «Эксперт и журнал» — подтверждение библиографии, экспертная оценка источника, решение по статусу с причиной и основанием, журнал всех событий;
   - «Подробнее» — причины, рекомендации, предупреждения, технические данные.
5. Повторная проверка после изменения данных не удаляет журнал. Изменение источника снимает его подтверждения.
6. Выгрузка результатов в JSON; подтверждения при загрузке не восстанавливаются.
7. Данные живут только в открытой вкладке.

## 17. Черновик обоснования, полнота реестра, тестовые подтверждения, устаревание (v0.5)

1. **Черновик** (`buildJustificationDraft(input, result)`) формируется только по результату движка. «Не урегулировано» в тексте появляется лишь если движок его установил; при «невозможно проверить» — «отношение установить не удалось; утверждать, что протокол вопрос не регулирует, нельзя». Если статус не «Обоснованное отклонение», черновик содержит «обоснование пока не может считаться достаточным», перечень недостающего и причины блокировки. Первая строка: «ТЕСТОВЫЙ ЧЕРНОВИК» и основа анализа.
2. **Основа анализа** (`analysis_basis`) входит в каждый результат и показывается в интерфейсе.
3. **Полнота реестра**: подтверждение эксперта с числом протоколов; изменение перечня или ответа о полноте снимает подтверждение.
4. **Тестовые подтверждения**: метка «ТЕСТ» на подтверждениях, решениях, записях журнала и черновике; `test_confirmations_used` в результате.
5. **Устаревание**: отпечаток входных данных сохраняется в результате; при расхождении карточка помечается «Устарел», решение по статусу и черновик недоступны до повторной проверки; история решений и прежние результаты (`prior_results`) сохраняются.

## 19. Требования этапа 4 к реестру (после проверки PR №6)

1. Наличие URL не доказывает действие редакции. Статус «действует» в реестре — только при официальном подтверждении документа, проверке актуальности редакции (`currency_check`) и подтверждении эксперта.
2. Положительный вывод модуля требует в записи реестра `official_evidence` (официальный документ) и `currency_verified: true`. Ручная отметка статуса или подтверждение эксперта без этих данных его не разблокируют.
3. Документ идентифицируется `doc_id` (тип:название:дата). Номер заседания ОКК общий для многих протоколов: если по номеру в перечне больше одного документа — «невозможно проверить».
4. Тип протокола: диагностика и лечение / медицинское вмешательство / реабилитация / не установлен (только из официальной шапки).
5. Блокировка из-за неполноты реестра сохраняется.
6. Редакции выбираются по дате оказания помощи; без проверенной истории редакций ни одна не считается заменённой (пример: НЭК №154 от 23.12.2021 и №185 от 28.07.2023).

## 18. Полнота реестра и привязка экспертной оценки (v0.6)

1. **Уровни полноты реестра:** заявлена пользователем → подтверждена экспертом (тест, с перечнем протоколов, версией и основанием) → сверена с официальными источниками (появится на этапе 4 вместе с верифицированным реестром). Положительный вывод по «не урегулировано» возможен только на последнем уровне. Если в перечне подтверждения нет хотя бы одного просмотренного протокола, полнота считается не подтверждённой.
2. **Привязка экспертной оценки.** Оценка хранит отпечаток контекста (псевдоним пациента, назначение со схемой, показания) и ключ источника (название, PMID, DOI). При расхождении оценка не учитывается, источник получает «нужна повторная экспертная оценка», статус — «Требуется оценка эксперта». Библиографическое подтверждение остаётся, пока не изменился сам источник.
3. Следствие для тестовой версии: «Обоснованное отклонение» достижимо только при отклонении от протокола, где совпавший протокол подтверждён (например, доза вне диапазона). Для «прямой рекомендации нет» окончательного положительного вывода не будет до этапа 4. Это намеренно.
