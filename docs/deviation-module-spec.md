# ТЗ: модуль «Отклонение от протокола + обоснование» (Антидефект, версия 0.3)

Статус документа: после второй экспертной проверки (PR №3). Разработка ведётся по этапам (раздел 15). Этапы 1–2 реализованы в `engine/`.

Изменения относительно 0.2:
- клиническое соответствие и полнота обязательной документации — две отдельные оценки; положительный клинический статус не скрывает отсутствующие записи (раздел 5.3);
- противоречия в клинических данных выявляются отдельно (`conflict_detected`) и не подменяются статусом «Недостаточно данных» (раздел 5.4);
- сигналы безопасности получили серьёзность, уверенность и подтверждённость; срочность определяется по порогу (раздел 7);
- библиографическая проверка источника (PubMed) отделена от экспертной оценки доказательств (раздел 4, блок 3);
- приняты решения по открытым вопросам версии 0.2 (раздел 13).

## 1. Принцип

Единственный критерий аудита: помощь оказана по действующему протоколу РК. Отклонение от протокола не является дефектом само по себе, но каждое существенное отклонение должно иметь проверяемое обоснование. Отсутствие рекомендации в протоколе не означает запрет назначения. Наличие публикации не означает, что назначение обосновано.

Программа не выносит окончательного решения и не объявляет врача допустившим дефект. Она показывает, чего в обосновании хватает и чего нет. Окончательное решение принимает назначенный врач-эксперт или уполномоченная комиссия медицинской организации.

## 2. Объект проверки

Проверка выполняется отдельно по каждому назначению или решению: препарат, доза, кратность, путь введения, длительность, метод, исследование.

## 3. Два независимых параметра

### 3.1. Отношение к протоколу

| Значение | Условие |
|---|---|
| Соответствует | Протокол регулирует вопрос, назначение в пределах указанного (включая допустимый диапазон) |
| Отличается | Протокол регулирует вопрос, назначение выходит за его пределы |
| Не урегулировано | В проверенном наборе применимых протоколов прямая рекомендация не найдена |
| Невозможно проверить | Нет данных для сравнения, нет ссылки на протокол (номер, раздел, цитата), редакция на дату помощи не подтверждена, либо для «не урегулировано» нет перечня просмотренных протоколов и сведений о полноте реестра |

Формулировка для «не урегулировано» всегда такая: «прямая рекомендация не найдена в проверенном наборе применимых протоколов». Формулировка «в протоколах РК рекомендации нет» запрещена.

### 3.2. Подтверждение показаний

| Значение | Условие |
|---|---|
| Подтверждены | В истории есть данные, соответствующие показанию |
| Не подтверждены | Проверена полная история, подтверждающих данных нет |
| Недостаточно данных | Предоставлен только фрагмент истории или данных мало |

«Не подтверждены» допустимо только при полной истории. Параметры 3.1 и 3.2 независимы.

### 3.3. Допуски по дозам

Универсальный допуск не применяется. Сравниваются конкретные параметры (доза на кг, разовая и суточная доза, интервал и т. п.) с диапазонами, прямо установленными протоколом или инструкцией. Назначение внутри диапазона отклонением не считается. Если диапазоны заданы, результат сравнения имеет приоритет над заявленным отношением.

## 4. Пять блоков проверки

Каждый факт хранится с источником: дата, время, фрагмент истории, раздел документа.

1. **Назначение.** Что назначено; результат поиска по протоколам (раздел 6); значение 3.1; в чём отличие.
2. **Показания.** Факты из истории и значение 3.2. Программа ничего не домысливает.
3. **Научное обоснование.** Две независимые проверки:
   - **Библиографическая (автоматическая):** источник существует; PMID/DOI, название, авторы, год, журнал совпадают с указанными. Инструмент — NCBI E-utilities (PubMed) или ручная проверка. Результат: найден / не найден / метаданные не совпадают. Эта проверка ничего не говорит о качестве и применимости исследования.
   - **Экспертная оценка (только человек):** применимость к ребёнку (совпадает / частично / не совпадает / не определено) и соответствие схемы (да / частично / нет / не определено). Записывается, кто оценил.
   Источники программа не выдумывает.
4. **Документация.** Запись врача с обоснованием, оценка пользы и рисков, мониторинг, консилиум, согласие. Для каждого: найдено / не найдено в предоставленном фрагменте / не найдено после проверки полной истории.
5. **Вывод.** Клинический статус (раздел 5), состояние документации (5.3), сигналы безопасности (раздел 7), противоречия (5.4).

## 5. Статусы

### 5.1. Приоритет

Программа предлагает один клинический статус. Выбирается первый подходящий.

| № | Статус | Условие |
|---|---|---|
| 1 | Требуется срочная оценка эксперта | Есть сигнал безопасности выше порога срочности (раздел 7) |
| 2 | Требуется оценка эксперта | Обнаружено противоречие (5.4) или есть сигнал безопасности ниже порога срочности |
| 3 | Недостаточно данных | Отношение «невозможно проверить», показания «недостаточно данных», либо при отклонении обязательные записи «не найдены во фрагменте» |
| 4 | Соответствует протоколу | Отношение «соответствует», показания подтверждены |
| 5 | Обоснованное отклонение | Отношение «отличается» или «не урегулировано», выполнены все условия 5.2 |
| 6 | Требуется оценка эксперта | Все условия 5.2 выполнены, кроме экспертной оценки применимости или схемы |
| 7 | Отклонение документировано не полностью | Остальные случаи; перечисляется, чего именно нет |

Статус «Потенциальный дефект» автоматически не ставится. Его может установить только эксперт (5.5).

### 5.2. Условия «обоснованного отклонения»

Все одновременно:
- показания подтверждены;
- хотя бы один источник предъявлен, прошёл библиографическую проверку и оценён экспертом;
- применимость «совпадает» и схема «совпадает», либо хотя бы одно «частично» при наличии записи врача о причине переноса данных;
- запись врача с обоснованием найдена;
- консилиум проведён, если он обязателен (раздел 8).

Статус не означает, что назначение доказанно правильное и что комиссия его примет.

### 5.3. Полнота документации

Оценивается отдельно от клинического статуса по списку обязательных записей:
- обязательные записи из правила реестра (для назначений по протоколу);
- для отклонений — всегда запись врача с обоснованием, плюс консилиум, если он обязателен, плюс записи из настроек.

Состояние: полная / неполная (не найдено в полной истории) / не определена (не найдено во фрагменте) / не требуется.

Итоговая строка заключения всегда показывает оба результата, например: «Соответствует протоколу; документация неполная: запись врача с обоснованием». Положительный клинический статус не скрывает отсутствующих обязательных записей.

### 5.4. Противоречия (`conflict_detected`)

Противоречие — два факта из истории, которые не могут быть верны одновременно (например, разные результаты одного посева). Каждое противоречие хранится парой фактов с источниками. При любом противоречии статус «Требуется оценка эксперта» (приоритет 2), а не «Недостаточно данных».

### 5.5. Ручное изменение

Эксперт может изменить любой статус, включая установку «Потенциальный дефект», с обязательным указанием причины и источника. Исходный результат программы сохраняется; все изменения записываются в журнал.

## 6. Поиск по протоколам

Для каждого назначения сохраняется: перечень просмотренных протоколов (номер, дата утверждения, редакция, статус в реестре, подтверждение редакции на дату помощи), проверенные разделы, критерии применимости, дата поиска, полнота реестра (сколько протоколов, какие применимые не внесены).

Статус протокола в реестре: действует / заменён / не проверен. Протоколы, актуальность которых не подтверждена официальным источником, имеют статус «не проверен». Старый год утверждения сам по себе не означает отмену.

Если редакция протокола на дату оказания помощи не подтверждена, отношение к протоколу «невозможно проверить».

## 7. Сигналы безопасности

Сигнал — предупреждение о риске, а не заключение о дефекте. Виды: возможное противопоказание, возможное превышение дозы, возможное несоответствие пути введения, возможное несоответствие интервала.

Каждый сигнал содержит:
- **серьёзность:** низкая / средняя / высокая / критическая;
- **уверенность:** низкая / средняя / высокая;
- **подтверждённость:** подтверждён документально или нет;
- цитату требования, факт из истории и источник.

Сигнал срочный, если серьёзность не ниже порога («высокая» по умолчанию) и он подтверждён либо уверенность не ниже порога («средняя» по умолчанию). Пороги задаются в настройках и подлежат утверждению экспертом. Срочный сигнал — статус 1, несрочный — статус 2.

На этапе 2 сигналы поступают на вход модуля. Автоматическое формирование сигналов из инструкций препаратов — этап 4.

## 8. Консилиум

Консилиум не обязателен автоматически при отклонении. Обязателен только при наличии нормативного или локального основания, указанного в настройках (без указания основания настройка не принимается). В остальных случаях программа рекомендует консилиум при высоком риске: применение вне инструкции, высокий риск по отметке врача, любой сигнал безопасности.

## 10. Требования к работе с данными

- До проверки правовых оснований обработки, требований к хранению и информационной безопасности в РК используются только синтетические или обезличенные истории.
- Псевдонимизация не равна полной анонимизации. Отметки согласия в программе недостаточно для работы с реальными данными.
- Модуль отклоняет входные данные, содержащие последовательность из 12 цифр (возможный ИИН).
- Исходная история не изменяется: модуль только читает.
- В PubMed передаются только библиографические данные (PMID, DOI, название), никаких данных пациента.
- ИИ используется только для извлечения фактов. Статус определяется детерминированными правилами разделов 3–8.

## 11. Пример

Назначен лечебный курс противогрибковой терапии ребёнку без порока развития диафрагмы.

В проверенных применимых разделах протоколов №4 (РДС), №185 (сепсис) и №231 (пороки развития диафрагмы) не обнаружена универсальная схема лечебной противогрибковой терапии для данной клинической ситуации. Отношение к протоколу: «не урегулировано».

Назначение требует оценки клинических показаний, микробиологических данных, факторов риска, научного обоснования и документированного решения врача. Само отсутствие прямой рекомендации не является основанием для квалификации назначения как дефекта.

Это пример логики, а не подтверждение правильности конкретного назначения.

## 12. Критерии приёмки

1. Параметры 3.1 и 3.2 независимы; есть тест «отличается» + «показания не подтверждены».
2. «Не урегулировано» не ставится без перечня просмотренных протоколов и полноты реестра.
3. «Недостаточно данных» и «не найдено во фрагменте» не превращаются в «не документировано» или в дефект.
4. «Потенциальный дефект» автоматически не ставится.
5. Срочность сигнала определяется по серьёзности, уверенности и подтверждённости; несрочный сигнал даёт статус 2.
6. Противоречие даёт статус 2, а не «Недостаточно данных».
7. Клиническое соответствие при отсутствии обязательной записи показывает «документация неполная».
8. Библиографическая проверка без экспертной оценки не даёт «Обоснованного отклонения».
9. Назначение внутри диапазона протокола не считается отклонением.
10. Ручное изменение статуса сохраняет исходный результат.
11. Исходные данные не изменяются.
12. Не менее 15 синтетических случаев, не менее 2 на каждый автоматический статус.

## 13. Решения по открытым вопросам

| Вопрос | Решение |
|---|---|
| Статусы для A/B/C | Единый набор статусов; отношение к протоколу и показания — отдельные параметры |
| Несущественные отклонения | Без универсального допуска; внутри диапазона — не отклонение |
| Консилиум | Обязателен только при нормативном или локальном основании; иначе рекомендация по риску |
| Актуальность 29 протоколов | Пока «не проверен». Каждый сверяется по официальным источникам с фиксацией редакций и дат. Реестр не заполняется предположениями |
| Кто подтверждает «проверено» | Назначенный врач-эксперт или уполномоченная комиссия |
| PubMed | Автоматическая библиографическая проверка (NCBI E-utilities); применимость и достаточность — экспертная оценка |
| Инструкции к препаратам | Приоритет — официальные государственные реестры РК (НЦЭЛС и МИ), с версионированием; международные источники — дополнительные, с явной маркировкой |

## 14. Открытые вопросы

1. Утвердить пороги срочности сигналов (по умолчанию: серьёзность ≥ «высокая» и подтверждён или уверенность ≥ «средняя»).
2. Кто и по каким официальным источникам подтверждает актуальность протоколов в реестре.
3. Какие записи обязательны для каждого правила реестра (поле `required_documentation`).
4. Можно ли из HTML-программы обращаться к NCBI E-utilities напрямую или нужен отдельный сервер.

## 15. Этапы разработки

1. Модель данных и независимые проверки — `engine/deviation-engine.js` (готово).
2. Детерминированный механизм статусов с тестами — `engine/test/` (готово).
3. Простой интерфейс аудита и формирования обоснования.
4. Подключение проверенного реестра протоколов и инструкций; формирование сигналов.
5. Синтетические клинические тесты и независимая проверка.

Реальные персональные данные не используются. `neo-pro` и `main` не изменяются. Изменения — через PR, без автоматического слияния.
